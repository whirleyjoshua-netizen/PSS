# The Customer Project Page, Phase 1 — Design

**Date:** 2026-09-16
**Status:** Approved in conversation, pending the owner's review of this spec.
**Scope:** The customer's project page becomes the page in the owner's mockup (minus the hero image): a dated seven-step tracker, project details, photos **and documents**, an updates timeline, contact and referral. Documents become shareable — private by default, with an explicit tick.

**Phase 2, specced separately:** "Approve quote" (moves the job to Sold and emails the owners) and "Acknowledge installation".

This builds on the customer portal, the job tracker, the appointments feature and file sharing, all of which are live.

## 1. Purpose

**The problem.** The customer page is a heading, a four-item text list, shared photos, a referral block and two links. It reads like a status endpoint, not like the business that just sold them shutters. Customers also have nowhere to find their paperwork — quotes and POs live in the owners' email.

**The fix.** The page in the mockup: where the project stands, when each step happened, what was ordered, the paperwork, the photos, and how to reach the owners — all on one page the customer can return to whenever they like.

**Success means:**
- A customer opens their link and can see, without asking: what stage their project is at and when each step happened, what they ordered, and every document the owners chose to share.
- The owners can attach a quote or PO to a job, tick "share", and the customer has it immediately.
- Nothing internal — notes, gate codes, money, lost reasons — can reach the page.

## 2. Decisions made in conversation

- **Magic link stays the only way in.** No passwords, no reset flow, no stored credentials. The existing 30-day `pss_customer` session already lets customers come and go; signing back in means requesting a new link.
- **Measurements step date** comes from the most recently saved measurement on the job.
- **Project Details shows the window count only** — no room count, which is not tracked.
- **No messaging.** "Message Premier" is cut; the phone number and email address stay.
- **Documents are private by default**, with an explicit per-file tick to share, exactly like photos today. File type (Quote, PO, Invoice, Other) is a separate label and never implies sharing.
- **No hero image.**
- **A short project number** (`PSS-1048`) is added, because the mockup shows one and customers need something to quote on the phone.

## 3. The security boundary (the most important section)

`lib/portal/access.ts`'s `toProject()` is a six-field whitelist, and `ProjectView` renders only from it. That property must survive this change.

`ProjectSummary` gains exactly these fields, each justified:

| Field | Source | Why it is safe |
|---|---|---|
| `projectNo` | `leads.project_no` | A display number, no other meaning |
| `windowCount` | `leads.window_count_exact` | The customer's own window count |
| `treatmentTypes` | `leads.treatment_types` | What they are buying |
| `finish` | `leads.finish` | What they chose |
| `orderedOn` | `leads.ordered_on` | Their own order date |
| `steps` | derived (§5) | Dates only, no free text |
| `documents` / `photos` | shared files only | Explicitly ticked by an owner |

**Never added:** `notes`, `gateCode`, `lostReason`, any `*Cents`, `budgetTier`, `source`, `heardVia`, `phone`, internal ids, or any `job_events` body.

A test asserts that `JSON.stringify(toProject(job))` contains none of: the notes text, the gate code, the lost reason, any money figure, or the budget tier — the existing test of this shape is extended rather than replaced.

## 4. Data

Migration `db/migrations/016_project_page.sql`, idempotent, whole-line `--` comments only, no `;` inside comments:

1. `alter table leads add column if not exists project_no integer` plus a sequence, or `generated by default as identity` if simpler — every existing job gets one, and new jobs get the next. Displayed as `PSS-<project_no>`, padded to four digits.
2. `alter table job_files add column if not exists doc_type text` with a dropped-and-re-added check: `doc_type is null or doc_type in ('quote','po','invoice','other')`.
3. No change to `shared_at` — it already exists on `job_files`.

`lib/admin/files.ts`:
- `setShared` currently hard-restricts to `kind = 'photo'` ("documents are never shared"). It is widened to allow `kind in ('photo','document')`. **This is the one place where a mistake exposes a document**, so the SQL keeps its `lead_id` guard, the activity entry keeps naming the file, and a test covers sharing and unsharing a document.
- A new `setDocType(jobId, fileId, type, actor)` sets the label. It never changes `shared_at`.
- `listSharedDocuments(leadId)` mirrors `listSharedPhotos`.

## 5. The seven steps

Customer-facing labels and their sources. Each step is `done`, `current` or `upcoming`, and carries a date when one exists.

| Step | Reached when | Date shown |
|---|---|---|
| Consultation | the job has passed `new` | the confirmed consultation appointment, else the first `new → visit_booked` stage event |
| Measurements | any measurement exists | the most recently saved measurement |
| Quote Ready | status is `quoted` or later | the first stage event reaching `quoted` |
| Order Confirmed | status is `sold` or later | the first stage event reaching `sold` |
| In Production | status is `ordered` or later | `leads.ordered_on` |
| Ready to Install | a confirmed install appointment exists | that appointment's date |
| Installed | status is `installed` or `completed` | `leads.install_on`, else the stage event |

Dates come from `job_events` rows of kind `stage` — **only their `created_at` and `to_status`**, never a body. A new `lib/portal/timeline.ts` reads them; nothing else about events reaches the portal.

The current step is the last one reached. "Estimated production 4–6 weeks" is a constant in `content/business`, shown only while In Production is current; it is not per-job data and the copy says "typically".

## 6. The page

Rebuilt to match the mockup, minus the hero. Existing tokens and type scale; no new design system.

1. **Header** — "Hi <first name>, your project is underway.", the address, `PSS-1048`, and Sign out. No hero image.
2. **Status banner** — the current step's headline ("Quote ready"), one sentence, and an action slot. In Phase 1 the slot holds **Review quote**, linking to the shared Quote document when one exists; otherwise the banner is informational. Phase 2 puts **Approve** here.
3. **Tracker** — the seven steps, horizontal on desktop, stacked on phones, with their dates.
4. **Next step** — what the customer should expect or do, with "Action required" only when there is something for them to do.
5. **Project details** — window count, treatment types, finish, estimated production (when relevant), and installation date or "Not scheduled yet".
6. **Installation** — the confirmed install appointment, or a line saying they will be notified.
7. **Project updates** — the dated stage events, rendered from a fixed label per stage. **Never** an event body.
8. **Photos & documents** — two tabs. Photos as today; Documents lists shared documents with their type label and a download link through the existing `/project/files/<id>` route, which already checks ownership.
9. **Contact** — phone and email, as today, restyled.
10. **Refer a friend** — the existing block, restyled to the mockup.

Everything works at ~400px. The tabs are real buttons with `aria-selected`, and the page renders correctly with JavaScript off (both tab panels present, the tab strip progressive).

## 7. The admin side

On the job's Files tab, each document gains: a **type** select (Quote, PO, Invoice, Other) and a **Share with customer** tick, matching how photos already work. The tick's label states plainly that the customer will be able to download it. An owner can untick at any time, which removes it from the portal immediately.

## 8. Error handling

- A job with no measurements, no appointments and no stage events still renders: every step is `upcoming` except Consultation, and no dates appear.
- A shared document whose blob is missing 404s through the existing file route rather than breaking the page.
- A customer with several projects keeps the existing list at `/project` and the new design on each project page.

## 9. Testing

**Unit (Vitest)**
- `toProject` leak test extended: no notes, gate code, lost reason, money or budget tier in the serialised output.
- The step builder: each step's reached/date logic, a brand-new job, a completed job, and a job whose install is scheduled but not done.
- `setShared` now allows documents, still refuses a file from another job, and unsharing clears it.
- `setDocType` sets the label and never touches `shared_at`.
- The timeline renders fixed labels, and no event body reaches the output.
- The page: tabs, the empty states, the action slot with and without a shared quote, and the project number's format.

**End-to-end (Neon test branch, production build, desktop)**
- Share a document from the admin, then open the customer link and download it from the Documents tab; untick and confirm it disappears.
- A job mid-flow shows the right current step with its dates.

## 10. Out of scope

- Approve quote and Acknowledge installation — Phase 2.
- Messaging between customer and owners.
- Passwords or any credential-based login.
- Room counts, per-job production estimates, and any money on the portal.
- Uploading documents from the customer's side.
